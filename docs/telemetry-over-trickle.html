Telemetry over Trickle

How runner-side metrics, errors, and lifecycle events are relayed over the trickle events channel to the local SDK client, which is the single point that publishes them to Kafka — or any other backend you plug in.

1 · The problem this solves

In cloud mode the GPU runner executes the full embedded Scope app, so every publish_event() call (session/stream/pipeline/error lifecycle) already fires on the runner. But the runner has no Kafka credentials — so those events silently no-op and were lost.

The Kafka code was never deprecated or removed — it's live, gated behind KAFKA_BOOTSTRAP_SERVERS. This change is a redirect: route the runner's telemetry over the trickle events channel so the client (which does have egress) publishes it, instead of relying on a broker the runner can't reach.

2 · How it works

One shared TelemetrySink protocol is used on both sides; only the implementation differs. publish_event() builds the event envelope once and hands it to whatever sink is active.

Key properties:

  • Stamp once, forward verbatim. The runner builds the envelope (id, timestamp, ids); the client re-publishes it unchanged via publish_raw_event(), only annotating relayed_via:"trickle" + a receive timestamp.
  • Backward compatible. When no sink is set, publish_event() falls back to the legacy direct-Kafka path — local (non-cloud) Scope is unchanged.
  • Best-effort, never blocking. A bounded queue with drop-oldest (mirroring the existing notification forwarder) means telemetry can never stall the media or control paths.
  • Distinct telemetry type. It does not reuse the notification channel — notifications are re-broadcast to the browser UI, telemetry must not leak there.

3 · The TelemetrySink seam

A sink is just one method. The same protocol is implemented three ways:

# server/kafka_publisher.py
class TelemetrySink(Protocol):
    def emit(self, event: dict) -> None: ...   # thread-safe, never raises, never blocks

class KafkaSink:          # client egress (default)        -> publish_prebuilt()
class LogSink:            # local testing, no broker        -> logger.info(...)
# cloud/trickle_events_sink.py
class TrickleEventsSink:  # runner forwarding over trickle  -> events_writer.write(...)

publish_event() selects the active sink; if none is set it uses the legacy global Kafka publisher. Stamping was lifted into a single build_event_envelope() so the runner stamps once and the client forwards the exact same bytes.

5 · Plugging in a client-side backend

The egress backend is chosen in exactly one place. To send telemetry somewhere other than Kafka, add a sink class and return it from the factory — nothing in the runner-relay or client-dispatch paths changes. 

# server/kafka_publisher.py
class HttpSink:
    def __init__(self, url: str): self._url = url
    def emit(self, event: dict) -> None:
        # POST event somewhere; must be non-blocking + never raise
        ...

def install_default_egress_sink() -> bool:
    if os.getenv("SCOPE_TELEMETRY_LOG_SINK"):
        set_telemetry_sink(LogSink()); return True
    # --- add your backend here ---
    # if os.getenv("TELEMETRY_HTTP_URL"):
    #     set_telemetry_sink(HttpSink(os.environ["TELEMETRY_HTTP_URL"])); return True
    publisher = get_kafka_publisher()
    if publisher and publisher.is_running:
        set_telemetry_sink(KafkaSink(publisher)); return True
    return False

The sink is installed on the client when it connects to the cloud (LivepeerConnection.connect → install_default_egress_sink()). The client is the single egress point; the runner only ever forwards over trickle.

Contract for a sink's emit(): it is called from worker threads, so it must be thread-safe, must never raise to the caller, and must never block. For network egress, hand off to a queue/loop (as KafkaSink does via publish_prebuilt) rather than doing I/O inline.

6 · Testing

Locally, without a broker (fastest)

The LogSink lets you watch relayed events without Kafka. Run the client with the flag and tail the logs: 

SCOPE_TELEMETRY_LOG_SINK=1 uv run daydream-scope --port 8022 --no-browser
# then, after a cloud session is running:
curl -s "http://localhost:8022/api/v1/logs/tail?lines=80" | grep TELEMETRY
# TELEMETRY type=runner_ready id=… session=… connection=… relayed_via=trickle
# TELEMETRY type=stream_heartbeat … (carries vram_*)
# TELEMETRY type=session_closed …

Unit-level (no infra)

The relay loop is exercised directly with a fake events writer:

  • emit from a worker thread via publish_event() → assert {"type":"telemetry","event":{…}} lands in order on the writer;
  • feed those messages to _handle_cloud_telemetry() → assert the egress sink receives the verbatim envelope (same id) plus relayed_via annotations.

Full local-cloud (two instances)

Follow .agents/skills/testing-livepeer/SKILL.md to bring up go-livepeer + a runner + the client, then run the HTTP sequence from CLAUDE.md (connect cloud → load passthrough → start a headless video-file session → run ~10s → stop). With SCOPE_TELEMETRY_LOG_SINK=1 on the client you should see runner_ready (with startup_ms), stream_heartbeat (with vram_*), and stream_stopped/session_closed — each carrying the runner's connection_id and relayed_via:"trickle".

Not yet run end-to-end / blockers. The two-instance local-cloud path and any real-GPU run were not executed during development — they require the prebuilt go-livepeer binary (PR #3884) and a CUDA GPU runner, which weren't available in the dev environment. What was verified: ruff lint/format, the full relay loop as an async unit test, 77 related tests, and a clean server boot. Before merging to production, run the full local-cloud flow above (and, ideally, point the client at a local redpanda to assert one Kafka message per event keyed by the runner's original id).

On cloud

  • Deploy a runner build with this change; the runner needs no Kafka config.
  • Configure the client egress: set KAFKA_BOOTSTRAP_SERVERS (+ KAFKA_SASL_* for Confluent) so install_default_egress_sink() picks KafkaSink.
  • Run a real session and confirm runner-origin events (e.g. runner_ready with startup_ms, media_*_loop_failed on induced failures) appear in your Kafka topic with data.relayed_via=="trickle".
  • Sanity: the runner must not double-publish — it has no broker, and the single global sink prevents double emit by construction.

TL;DR

The runner forwards every publish_event() over the trickle events channel as a telemetry message; the client receives it and re-publishes verbatim through a pluggable TelemetrySink (KafkaSink today, swap one factory for HTTP/other). The runner needs no broker; the client is the sole egress. New signals: startup time, media-loop errors, and VRAM. Verify locally with SCOPE_TELEMETRY_LOG_SINK=1; the full two-instance cloud run still needs a GPU + go-livepeer binary.
